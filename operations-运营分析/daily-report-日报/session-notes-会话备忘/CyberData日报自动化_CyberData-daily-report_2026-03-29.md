# CyberData 日报自动化会话备忘

日期：2026-03-29

## 目标

把 Lucky US 的日报推送改成真正离线可运行的链路，不依赖本机在线登录 CyberData。

目标链路：

1. CyberData 后台定时跑任务
2. 结果导出为 CSV 或结构化结果
3. 飞书侧接收文件/结果
4. 机器人汇总并推送日报

## 已确认的事实

### 1. 当前本机直连 CyberData 的方案不稳定

- 现有日报脚本依赖本机认证态和内部网络
- 手动 `dry-run` 时会在请求 `https://idpcd.luckincoffee.us` 阶段失败
- 当前机器上的 cron 实际配置时间与原预期不一致
- 结论：这条路不适合做“你电脑不在线也能跑”的正式方案

### 2. 同事大概率不是本机直连，而是服务端定时产出

根据飞书截图推断：

- `交易监控` 会定时在群里发多个 `day_*_data*.csv`
- `门店监控机器人` 再基于这些结果生成业务告警

推断出的架构是：

1. CyberData 或内部调度系统服务端定时跑数
2. 结果先导出到飞书群（CSV）
3. 下游机器人再消费这些 CSV，做告警/日报

## 当前对 CyberData 后台的判断

### 向导模式 API 不适合日报

用户已经在后台尝试过：

- 新建 API
- 向导模式
- 结构化
- 基于单表字段生成 API

遇到的问题：

- 很多字段被误设为请求参数，导致测试失败
- 即便修正后，本质仍是“单表条件查询 API”
- 这条路不适合做日报聚合

结论：

- 向导模式 API 只适合做最简单的单表查询/验证
- 不适合做多指标聚合日报

### `函数` 模式更像正确方向

用户在 CyberData 后台发现了函数入口（Python 模板）：

- 这更适合做聚合逻辑
- 后续应优先研究：
  1. 函数能否调用内部数据查询能力
  2. 函数能否被发布
  3. 函数/API 能否挂到周期任务

目前现状：

- 函数页面测试失败，但平台没有返回明确错误
- 继续在 UI 里盲试收益不高

## 下次继续时需要的材料

最好一次提供：

最好重点包含：

- env
- SQL 内容

获取方式：

1. 打开浏览器开发者工具 `Network`
2. 在 CyberData 里手动成功跑一次查询
3. 找到真实请求
4. 右键 `Copy as cURL`

## 下次继续时的起点

拿到真实 `curl` 后，优先判断哪条路最可行：

### 路线 A：后台定时 + 直接导出

如果 CyberData 自带：

- 周期任务
- 结果导出
- 飞书/邮件/文件推送

则优先走这条

### 路线 B：函数/API + 周期任务

如果 CyberData 支持：

- 函数运行
- 发布为 API
- API 挂周期任务

则可以让函数返回日报结构，再由任务调度

### 路线 C：外部脚本复用真实调用链

如果 CyberData 不支持结果推送，但 `curl` 链路稳定：

- 可以复用真实 `curl` 调用方式
- 放到常驻环境执行
- 再把结果推送飞书

## 当前结论

这次排查的关键结论不是“日报脚本怎么改”，而是：

- 问题核心在上游自动化入口
- 需要先拿到 CyberData 的真实可调用链路
- 再决定是“平台内调度”还是“平台外调度”

拿到 `curl` 之后，再继续。
