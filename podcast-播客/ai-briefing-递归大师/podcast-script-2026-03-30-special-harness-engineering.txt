特别版｜Harness Engineering：程序员不再写代码后，真正要掌舵的是什么 播客脚本

主持人：递归、大师
段数：59，字数：4355

————————————————————————————————————————

递归：大家好，我是递归。今天这期特别版，我们不追热点拼盘，只讲一个最近特别值得搞明白的新词：Harness Engineering。

大师：对，这个词表面上像又一个 AI 新名词，实际上它很可能是在重新定义工程师怎么和 Agent 一起工作。

递归：先说结论。Harness Engineering 不是 Prompt Engineering 的增强版，也不是“提示词写得更高级”。它更像在说：当 Agent 已经能写很多代码以后，人类真正该做的，不再是亲手写每一行，而是给 Agent 搭一个能持续干活的工作系统。

大师：这个判断来自 OpenAI 那篇官方文章。OpenAI——就是做 ChatGPT 和 Codex 的那家公司——做了一个内部实验：五个月，从空仓库开始，做出一个真实可上线、有人在用的内部产品，而且没有一行代码是人手写的。

递归：这个数据一出来，很多人第一反应是，完了，程序员是不是要下岗了。

大师：但文章真正想表达的恰恰不是这个。它给出的总纲非常明确：Humans steer, agents execute。白话就是，人类负责掌舵，Agent 负责执行。角色没有消失，但工作重心变了。

递归：也就是说，工程师从“写代码的人”，慢慢变成“设计环境、规定目标、审核反馈回路的人”。

大师：没错。你可以记一个锚点：以前工程师像亲自下场拉车的人，现在更像在设计轨道、仪表盘和刹车系统的人。车还是要跑，但重点从“我怎么拉”变成“这套系统怎么跑得稳”。

递归：那为什么 OpenAI 要专门发明 Harness Engineering 这个词？Harness Engineering——说白了就是 Agent 的执行装置工程——直接说 AI coding 不行吗？

大师：因为普通 AI coding 讲的是“模型会写代码”，Harness Engineering 讲的是“模型周围那一整套让它可靠工作的装置”。harness 这个词本来就有马具、控制装置、系带系统的意思，重点不在马有多快，而在你怎么把它驾驭起来。

递归：这个类比太好了。Agent 本身像马，Harness 是马具。没有马具，马再猛，也可能拉翻车。

大师：对。所以这篇文章最有价值的，不是讲 Codex 多聪明，而是讲 OpenAI 怎么给 Codex 造工位、造流程、造护栏、造证据系统。真正拉开差距的，越来越是 Harness，而不是单点模型能力。

递归：这个区别特别值得记。模型能力更像发动机马力，Harness 更像传动系统、刹车、方向盘和仪表盘。你不能只看发动机多猛，还得看整辆车能不能连续安全地跑。

大师：而且 Harness 最大的价值，是把好结果从“偶尔出现”变成“可以重复”。一次惊艳输出不难，难的是让 Agent 在十次、百次任务里都不太跑偏，这就必须靠环境，不可能只靠一句 prompt。

递归：好，那我们先拆第一个特别反直觉的点：这套实验是从一个空的 Git 仓库开始的。连第一版 AGENTS.md 都是 Agent 自己写的。为什么他们要把条件搞这么极端？

大师：因为他们故意切断“人类下场补洞”的退路。只要允许工程师随手改几行，很多结构性问题就会被掩盖。OpenAI 想验证的是：在没有人工代码当拐杖的时候，到底缺哪些能力，系统怎样才能自己走起来。

递归：也就是这不是偷懒，而是刻意练习。逼自己不能说“算了我来改一下”，只能回头问：Agent 为什么做不好，环境哪里没定义清楚。

大师：对，这个问题特别关键。Harness Engineering 的思维方式，不是任务失败了就骂模型，而是先问三件事：目标够不够清楚，反馈够不够及时，约束能不能被机器执行。很多团队卡住，不是模型差，而是这三件事没搭起来。

递归：那这就引出第二层了。工程师的角色到底怎么变？

大师：文章里最重要的角色转换是：从执行者变成掌舵者。以前你接到需求，自己拆、自己写、自己调。现在你更多是在定义系统目标，把任务拆成 Agent 能做的小块，再设计一个能不断纠偏的流程。

递归：听起来有点像产品经理加架构师加技术负责人，混成了一个新角色。

大师：很像，而且还要补一个能力：控制论思维。你不是一次性下命令就完了，而是持续观察系统状态，看目标和现实有没有偏差，再设计新的反馈机制把它拉回来。这也是为什么有中文解读把它比作 Agent 时代的控制论。

递归：这个比法我喜欢。以前像手拧阀门，现在像设计自动调速器。人不再一直在那儿拧，但得保证系统自己会调。

大师：对，瓦特调速器、Kubernetes 控制器，到现在的 Agent Harness，本质上都是同一件事：把反馈回路做成系统，而不是留给人肉补救。

递归：好，接下来我觉得是整篇文章最硬核也最能落地的一段：可观测性和反馈测试。可观测性——也就是 UI、日志、指标、trace 这些证据层——为什么对 Agent 这么关键？

大师：因为没有证据，Agent 就只是在猜。你让它“修好这个 bug”，如果它看不到页面、看不到日志、看不到性能指标，它最多只是生成一段看起来像答案的代码。真正的工程，不是写了什么，而是能不能证明结果达标。

递归：也就是说，Prompt 里那句“启动时间必须小于 800 毫秒”，只有当 Agent 真能查指标时，才不只是文学表达。

大师：对，而且这是 Harness 和普通自动补全最本质的差别。自动补全只负责给你候选代码，Harness 则要求 Agent 自己去找证据、跑检查、看是否达标。前者是在猜答案，后者是在跑实验。

递归：所以我们可以把它理解成：Agent 不只是个写作者，还是个实验员。它写完以后要自己去看数据、看页面、看错误日志，确认现实世界有没有真的变好。

大师：完全正确。文章里提到，他们把 UI、日志、指标和追踪都接给 Codex，而且每个 worktree 还是隔离的临时环境。这样 Agent 不只是能写代码，还能自己复现 bug、验证修复、检查关键路径是不是超时。

递归：这一层特别重要。很多人以为提高 Agent 质量，就是把模型换大一点。可 OpenAI 这里给出的答案更像是：先把感官和仪表盘装上。

大师：对。你可以记一个锚点：没有可观测性，Agent 只是会打字；有了可观测性，Agent 才开始像工程师。它第一次能根据证据回头修正自己，而不是靠概率硬猜。

递归：而且文章里有个细节很震撼，他们说经常看到 Codex 连续工作六个小时，还是在人类睡觉的时候。听起来像是在说：真正的产能，不是你让它更快敲字，而是你让它在反馈回路里更久地自己跑。

大师：对，这才是 Harness 的价值。不是帮你省十分钟，而是帮你把“可持续执行时间”拉长。单次聪明不值钱，持续可靠才值钱。

递归：接下来是我最想讲给所有 Builder 听的一条：给 Codex 一张地图，而不是一本一千页说明书。AGENTS.md——也就是仓库里的导航地图——为什么会变得这么重要？

大师：因为上下文是稀缺资源。OpenAI 一开始也试过把所有规则、注意事项、业务逻辑全塞进一个超大的 AGENTS.md，结果失败了。原因很简单：文档一大，Agent 就会迷路，漏掉关键约束，或者被过时规则误导。

递归：也就是说，大而全并不等于高质量上下文。对 Agent 来说，一千页说明书很可能不是帮助，而是噪音。

大师：没错。因为 Agent 不是慢慢翻书的人，它更像高频决策的执行者。你给它的入口越混乱，它每次检索和判断的成本就越高，最后不是忘重点，就是抓住了早就过时的信息。

递归：所以知识组织方式本身，就是 Harness 的一部分。不是写了文档就算完成，而是要问：这个文档是不是能被 Agent 稳定找到、正确理解、持续维护。

大师：没错。所以他们把 AGENTS.md 变成一张导航地图，大约一百行，只负责告诉 Agent 去哪儿找真正知识。真正的事实来源被拆进结构化 docs、设计文档、执行计划、产品规格、质量评分这些仓库内工件里。

递归：这个思路跟我们平时做 AI 协作也很像。不是一上来把所有话都说完，而是给它一个稳定入口，再做渐进式披露。

大师：对，这里你可以记一个锚点：AGENTS.md 不该是百科全书，而该是索引页。入口越小越稳，知识越深越结构化，Agent 越不容易在上下文里溺水。

递归：而且 OpenAI 还不只停在“写出来”这一步。他们用 lint 和 CI 去检查知识库有没有过期、有没有断链、结构是不是合法，甚至安排了一个专门的“文档园丁” Agent 去扫陈旧描述。

大师：这个点非常高级。很多团队只想着让 Agent 读文档，却没想过文档本身也会腐坏。可一旦文档过期，它不是中性的，它会主动把 Agent 带偏。所以文档维护也必须进入 Harness。

递归：好，最后来到秩序维护这一层：架构围栏、质量评分、垃圾回收。为什么 Agent 时代比以前更需要这些东西？

大师：因为 Agent 会复制模式，而且复制速度极快。仓库里有什么风格、什么坏味道、什么历史烂习惯，它都会学，而且会规模化放大。人类工程师有时会偷懒，但一天也写不了那么多；Agent 一旦跑起来，几小时就能把坏模式扩散到整片代码库。

递归：所以以前技术债像慢性病，现在更像高传染性疾病。

大师：这个比喻很准。OpenAI 后来做的事，就是把风格、分层、架构约束编码进 linter、结构测试、质量文档和后台修复任务。文章里甚至把这类后台任务类比成垃圾回收。意思是，代码库会自然产生漂移和熵增，你得持续自动清理，而不是等它烂透再大扫除。

递归：这也解释了为什么他们对合并哲学都开始重写。吞吐量一上来，门禁怎么设、哪些问题先放过去、哪些问题必须当场卡死，都会变成系统设计问题。

大师：对。Agent 时代的软件工程，不只是“能不能生成”，而是“能不能在高吞吐下还保持秩序”。Harness 本质上就是这套秩序装置。

递归：好，收尾前我想把它压成一句最白的话。Harness Engineering 到底是什么？

大师：一句话版：不是教 Agent 多说几句人话，而是给 Agent 搭一个能稳定干活、能自证结果、能持续纠偏、能防止失控的工程环境。

递归：那对我们这些 Builder 来说，最先该学什么？

大师：三个动作。第一，别再只优化 prompt，开始补反馈回路。第二，把知识放回仓库，用索引加结构化文档替代大杂烩。第三，把架构约束写成机器能检查的规则，而不是只写在人脑里。

递归：我再补一个。以后看 Agent 产品，不要只问它底层模型是谁，还要问：它有没有日志、有没有测试证据、有没有可观测性、有没有记忆地图、有没有自动清债机制。没有这些，再强也只是会写字。

大师：完全同意。Prompt Engineering 解决的是“怎么开口”，Harness Engineering 解决的是“怎么长期运转”。后者才更像下一阶段真正的护城河。

递归：这期特别版就到这儿。我们不是在听一个新名词，而是在看软件工程的角色重排：程序员不消失，但越来越像掌舵人，而不是划桨人。
